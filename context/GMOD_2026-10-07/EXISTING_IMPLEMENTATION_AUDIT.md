## Verified current menu and input paths

Initial direct reads covered current `main.cpp` lines 4781–4970 and 6301–6630, plus `gmod_overlay.inc` lines 1–620 and 681–878. The root subsequently supplied a private, ignored full-text cache of the same source, normalized from CRLF to LF. Local inspection extended to acquisition/hold/throw/actor/audio/tool/action/weapon/lifecycle procedures; hashes above identify the protected Windows originals, not normalized cache bytes. No cached implementation payload is published by this report. Exact function names and line numbers remain evidence anchors.

`PollControls` waits for gameplay readiness, a loaded player cell and `GameHasFocus`. It polls Q/F2 with `GetAsyncKeyState(... & 0x8000)` and calls `ToggleBuildMenu` on a rising edge. Q release does not close the menu. While the build menu is open, the dispatcher processes its controls/pending spawn/tests/beam visibility and returns before ordinary equipped-weapon/skate dispatch. `OpenBuildMenu` requires a player cell, no active skate mode and registered categories. It snapshots/disables Fallout Fight and Movement flags; close restores each flag only if it was initially clear. The displayed menu also opens from R while the Tool Gun is active. Current inspected paths contain no E opener; E activation is an unconfirmed report requiring a bind/hook and deployed-version trace.

`ShowGModSpawnOverlay` creates a persistent Win32 popup HWND once, then repositions/shows/invalidates it. It uses `WS_EX_TOPMOST | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE` and `SW_SHOWNOACTIVATE`. It is **not** repeatedly recreated on every frame. `ResolveFalloutWindow` caches the first foreground HWND rather than checking that it belongs to Fallout. Positioning uses the outer window rectangle. The inspected overlay has no Source VGUI panel lifecycle, `MakePopup`, saved cursor-position contract, text-focus/hang-open behavior, or Source mouse/keyboard capture implementation.

The visible menu is manually painted with GDI/GDI+, fixed at 1140×720, with a six-column/five-row prop grid and Tahoma text. Categories and content come from compiled `kGModPropCategories`/`kGModPropDefs`. The displayed tools are hard-coded Duplicator and Remover at indices 7 and 29. Category selection, page navigation, item selection and click spawn are custom C++ handlers. This is a **temporary placeholder / recreated implementation**, consistent with the project's accepted decisions; its appearance is not proof of an original GMOD menu. Original registries, creation tabs, search, utilities, context menu, property sheets, model previews and VGUI layout are not implemented in this inspected path.

Preserve the menu dispatcher boundaries, menu-before-tool early return and existing safety checks as useful host integration evidence. Their correctness across all Fallout menus/save transitions is still untested. Preserve the compiled prop catalog as data for a future original-system adapter; it does not establish that every compiled entry is part of the prepared 290-entry curated catalog.

## Icons, flicker and browser defects

`LoadOverlayImage` opens files relative to the process working directory under `Data\NVSE\Plugins\FNVGModTHUG2_UI`. `EnsureOverlayImages` loads decoded content backgrounds/category glyphs and beam/glow PNGs. Original-pixel provenance is claimed by source comments for the Physgun sprites and requires matching the staging provenance manifest; the comments alone are not proof.

`LoadPropThumbnail` computes a lowercased-source-path FNV-1a 32-bit hash and opens `propicons\%08X.png`. It caches the result, including a null result. Missing files remain missing until process/cache reset. `IconForBuildProp` then shows generic NPC/car/gun/tool/package/bricks glyphs. Every displayed icon is squeezed into 52×52 pixels. This is **fallback/audit thumbnail support**, not original `SpawnIcon`/`ModelImage` model rendering or native icon generation. Keep original extracted glyphs and prepared previews, while retaining the distinction between authentic asset pixels and recreated rendering behavior.

Likely missing/incorrect-icon causes are a missing PNG, a producer/consumer path-hash mismatch, process working-directory mismatch, stale null cache, or generic fallback being mistaken for a model icon. Each is a source-grounded hypothesis; this pass did not inspect deployed image existence/hash-to-model pairing or reproduce the defect. Generated support geometry previews must not be promoted as substitutes for original GMOD icon semantics.

Menu paint uses an offscreen compatible bitmap and `BitBlt`, with `WM_ERASEBKGND` suppressed. `ShowBuildMenuStatus(false)` is a no-op, so that call does not invalidate every menu frame. Source evidence therefore does **not** support a blanket claim that menu flicker is caused by repeated menu creation or that status helper. Remaining hypotheses include topmost-window/fullscreen presentation conflict, wrong cached host HWND, competing input/menu visibility ownership, or a deployed DLL different from inspected source. Reproduce with frame/visibility/input logs before repairing runtime code. Source browser incompleteness is proven: it is a static paged grid without original search/model-preview architecture.

## Tool Gun selection and execution

Both hover and click on the two displayed tool buttons select a mode; footer text explicitly tells the player to hover to arm the Tool Gun. Original GMOD tool selection must instead follow its actual selected-tool command/convar/SWEP chain. There is also a small edge case: selecting the already-current index does not set `g_toolgunEnabled` because that assignment is inside the changed-index condition.

`PollControls` dispatches Tool Gun primary/secondary to `ToolgunPrimaryAction`/`ToolgunSecondaryAction`. Leafblower uses primary-held; other modes use primary-pressed. R opens the build menu and Z calls `UndoLastRemoved`. The same actions also run from F9/debug mode when no GMOD weapon is equipped. This is a **useful compatibility dispatch boundary plus incomplete/recreated tool behavior**, not evidence that original SWEP/stool Lua, prediction, tool screen or registry executes. The mode index and current weapon state need reconciliation with the real GMOD tool registry before preserving this as final selection semantics.

Full-source inspection found no `MessageBox`/Fallout dialog selector in these two files. That status (2529) still advertises “R next / Shift+R previous” although current R opens the menu and `CycleToolMode` has no caller in this source. ## Physgun, beam and actor bridge

Current equipped Physics Gun dispatch uses LMB **press** to toggle grab/drop and RMB **press** to `ThrowHeld` or dry-fire if nothing is held. R calls `UnfreezeRef(GetCrosshairTarget())`; bracket keys change hold distance using named range/wheel constants. This matches the current user's launch-direction requirement, but press-toggle does not prove original hold/release behavior. F7 debug mode has a separate legacy path: LMB grab/drop and RMB `FreezeHeld`. Physcannon uses a separate primary-punt/secondary-pickup mapping. Keep these identities separate. Earlier handoffs describing RMB grab/LMB launch do not override the current user's requested mapping.

Weapon switching drops a held ref when leaving a physics weapon if the debug Physgun flag is off. This is a **useful cleanup bridge**, pending lifecycle/playtest coverage. The extended inspection supports the following narrower diagnoses.

**Acquisition range:** `GetCrosshairTarget` (870) returns the Fallout `InterfaceManager::crosshairRef` from address `0x011D8A80`, rejecting null/player. `GrabCrosshairRef` (5034) uses that result directly. There is no independent extended Physgun raycast in the acquisition path. Constants at 736–745 and hold-distance clamping at 5096/5192 do not extend Fallout crosshair acquisition. The reported short usable range is therefore strongly consistent with an activation/crosshair-ref-limited bridge. Actual engine crosshair distance/settings and the deployed binary must be measured before naming the complete runtime cause. A trace adapter should retain the original trace mask, range, hitpoint, body/bone and permission semantics rather than increasing only hold distance.

**Holding and physics:** `UpdateHeldObject` (5177) computes a target from player position plus a hard-coded 58-unit eye offset and yaw/pitch times hold distance. It uses the held reference origin as error target, not a stored local grab hitpoint or chosen physics body/bone. It applies desired/damped linear velocity to a root prop rigid body or every usable ragdoll body, with movement-key spin, and teleports the reference when no usable body exists. Controller constants have original-source evidence comments, but those constants alone do not make this host controller equivalent to the Source shadow controller. Havok writes/offsets at 880–943 and ragdoll offsets at 809–824 are version-specific adaptation evidence requiring the IDA build checks. Preserve this implementation until an evidence-backed adapter replacement is reviewed; do not copy its fallback teleport semantics into a claimed original controller.

**Continuous hold audio:** `GetOrCreateGModSound` (1239) explicitly clears `kFlag_Loop` at 1256. `PlayGModSound` (1267) creates a 2D sound and invokes `playsound` on the player. The Physics Gun helpers at 1322–1353 play pickup/drop/dry-fire/launch one-shots using original-looking physcannon payload paths. No continuous hold sound start/update/stop lifecycle exists in the full inspected main/overlay source. This is a proven source-level omission consistent with the reported wrong/missing hold loop. Exact original event selection and native loop state remain to be recovered/verified; payload provenance and a one-shot path do not establish correct audio behavior.

**Actor identity:** `setunconscious 1` at 5055 explicitly executes with acquired `target`; `TrySetActorKnockedState` (797) uses that ref's Actor/BaseProcess. Those statements do not directly identify the player as the unconscious target. However, grab at 5056, throw at 5131/5137 and fallback throw at 5170 issue `pushactoraway player ...` with the acquired target as script context. The command's explicit actor argument is **player**. This is a strong source-level candidate for the reported player knockdown/impulse symptom; confirm the engine command's caller/argument semantics and actual affected ref in an isolated test before recording a proved gameplay cause. Do not silently swap command arguments without that check.

Actor drop (2422) restores the stored knocked state but unconditionally runs `setunconscious 0`; wake after throw (5303) does the same. Pre-grab unconscious state is not stored. The delayed wake scheduler has one ref id/tick/state slot; a second actor throw before the 3.5-second recovery overwrites the first actor's pending wake. These are concrete incomplete actor-state/persistence safeguards. Their observed severity and any crash consequences are untested. Acquisition/held/physics-body/player identities must remain distinct in the final compatibility layer.

`PaintPhysBeam` (overlay:505) draws a 2D strip from a fixed screen point (72% width, 80% height) to screen center. It shows only while a ref is held, uses active/white sprite PNGs, applies a fixed cyan matrix, and draws a center glow. It does not compute weapon attachment/bone origin, trace endpoint, held target hit point, world-space beam occlusion, player-selected color, or object silhouette/highlight. This is **authentic-pixel use pending provenance plus recreated/incomplete rendering**. Full main/overlay search found no halo/outline/highlight implementation in those files; an external backend has not been proven. The original sprite/material semantics and native beam state must drive a host render adapter rather than preserving this fixed-screen approximation as final behavior.

Original `garrysmod/gamemodes/sandbox/gamemode/cl_init.lua:127` receives `DrawPhysgunBeam(ply, weapon, bOn, target, boneid, pos)` and records the valid acquired target in `PhysgunHalos` when `physgun_halo` is enabled, returning true for native beam rendering. `PreDrawHalos` at 139 uses player weapon color plus random variation, size 1–2, `halo.Add`, then clears the per-frame target table. Current fixed cyan/glow rendering preserves neither that target hook nor its halo semantics. The original function does not itself specify the native beam endpoint algorithm; `pos`/`boneid` must be traced through native evidence before claiming the rendering implementation recovered.

## Decisions this evidence supports

Preserve provenance-backed original scripts/assets, validated curated data, safety/lifecycle guards, equipped-weapon identification and clean action/spawn boundaries. Repair input ownership and presentation only after proving the observed issue against current deployed identity. Replace the hand-painted menu, fixed-screen beam and index/hover tool selector as final-system implementations through original-system-compatible adapters, under Opus ownership. Do not classify a working component as no longer required without a traced original equivalent and regression evidence.

Additional input/lifecycle evidence: current E consumers are vehicle enter/exit (2308), custom button activation (2950), and THUG2 controls; none calls OpenBuildMenu. Menu openers in full main source are Q/F2, Tool Gun R and the `gmod_spawnmenu` NVSE command (6639). Original E activation report therefore remains unresolved in other mods/binds/ESP scripts/deployed identity. `PollControls` has no explicit Fallout menu-mode veto beyond loaded gameplay and process focus. Its menu early return leaves mouse-edge history unchanged and skips `UpdateHeldObject`/`UpdateThrow`, so a preexisting held rigid body may retain its last velocity and actor recovery timers wait while the menu is open. `MessageHandler` resets `g_buildMenu` on load/new game without calling `HideGModSpawnOverlay`; source window-state divergence is possible if a load occurs with the overlay visible. These are source-grounded regression cases, not reproduced flicker/crash causes.

Unresolved: external input hook/bind/E/deployed trace; native command actor semantics and isolated identity test; original native acquisition/hold/audio equivalence; deployed icon paths/pairing; menu flicker reproduction; complete model/load-order/inventory validation; Lua/native service coverage. No crash cause is newly proved from source inspection alone.
