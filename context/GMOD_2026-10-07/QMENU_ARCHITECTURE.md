## First vertical slice: input through visibility

The root investigator directly verified the installed command identities: `garrysmod/cfg/config.cfg:28` binds Q to `+menu`, and line 14 binds C to `+menu_context`; `config_default.cfg:51` and line 62 contain the same respective defaults. Controller binding definitions also use `+menu`. The configuration inventory records current-source SHA-256s: active config `EE298E04B3D29BAADBE26BA74A8D3BAE59907285D113F843EA34DF109DD34F0A`, default config `6FE58D8C55A3322093B1A99EC8E556A09AC97141046C38C0DFFDEB54E427FFF4`. Thus the bridge should translate Source command identities across rebound keyboard/controller inputs, rather than make the literal Q key the only original entry point.

The Lua endpoints are `GM:OnSpawnMenuOpen`/`GM:OnSpawnMenuClose` and their context equivalents. Native `+menu`/`-menu` command-to-hook dispatch remains a narrow IDA 6.8 boundary until the collector proves the actual build's command handlers and call relationships. Observing Q in the current FNV code does not prove that original dispatch.

`cl_spawnmenu.lua` includes `spawnmenu/spawnmenu.lua`. That file includes sibling `toolmenu.lua`, `contextmenu.lua`, and `creationmenu.lua`. `CreateSpawnMenu` runs from `OnGamemodeLoaded`, explicitly after scripted entities and weapons are loaded, and is also exposed as `spawnmenu_reload`. It checks `SpawnMenuEnabled`, removes an old menu only when recreating, clears tool-menu registration, runs the tool-tab/category/population hooks in order, creates `SpawnMenu`, initially hides it, calls `SpawnMenuCreated`, creates the context menu, and calls `PostReloadToolsMenu`.

The hook order is `PreReloadToolsMenu` → `spawnmenu.ClearToolMenus` → `AddGamemodeToolMenuTabs` → `AddToolMenuTabs` → `AddGamemodeToolMenuCategories` → `AddToolMenuCategories` → `PopulateToolMenu` → create panel → `SpawnMenuCreated` → `CreateContextMenu` → `PostReloadToolsMenu`. Ordinary open/close does not recreate the menu. Language changes may recreate it when closed and without unsaved spawnlist changes; otherwise they defer refresh. `SpawnlistContentChanged`, `OnSaveSpawnlist`, and `OnRevertSpawnlist` maintain that protection.

`GM:OnSpawnMenuOpen` records `SysTime`, asks the `SpawnMenuOpen` hook for permission, calls the persistent panel's `Open`, parents `menubar` to it, and calls `SpawnMenuOpened`. With `spawnmenu_toggle` enabled, opening an already visible menu returns early. `GM:OnSpawnMenuClose` ignores release within 0.180 seconds when toggle mode is enabled, then closes and dispatches `SpawnMenuClosed`. The archived default of `spawnmenu_toggle` is `0`; original default operation therefore has a press/hold/release contract, with explicit opt-in toggle behavior. The current FNV rising-edge Q/F2 toggle differs from that contract.

`SpawnMenu:Open` restores remembered cursor position, clears its own `HangOpen`, requests `Close` on a visible competing context menu, avoids repeating popup setup if already visible, closes Derma submenus, calls `MakePopup`, enables mouse input, disables keyboard input initially, restores alpha to 255, and reports `achievements.SpawnMenuOpen`. A competing menu's `Close` can consume its own HangOpen, so the call itself must not be interpreted as proof of hidden visibility. If a valid startup tool was saved it selects the panel, calls `spawnmenu.ActivateTool(tool.Name, true)`, and clears that startup pointer.

`SpawnMenu:Close` first consumes `HangOpen` without hiding. Otherwise it remembers cursor position while visible, closes Derma menus, disables keyboard and mouse input, and hides the persistent panel. `OnMousePressed` closes it. The `GUIMousePressed` hook returns true while it is visible, preventing context-world clicking; `GUIMouseReleased` closes the visible menu and returns true. A host bridge must preserve the distinction between GUI event delivery and world attacks/use.

`GM:OnSpawnMenuClose` still calls `SpawnMenuClosed` after the panel's `Close`, including when HangOpen made that method return without hiding. The bridge must observe actual panel/focus state rather than force visibility from the callback name alone. This nuance is essential to text-entry release behavior.

Text entries temporarily change ownership: `OnTextEntryGetFocus` checks panel ancestry and calls `StartKeyFocus` on the appropriate spawn/context menu. This sets keyboard input on and `HangOpen` true. `EndKeyFocus` disables it only for the tracked focus panel. Releasing Q during text entry can therefore consume a hang-open state; forcing visibility off every frame or indiscriminately forwarding keyboard events would discard original search/text behavior.

## Panel assembly and layout

`SpawnMenu` derives from `EditablePanel`, docks `FILL`, and owns a `DHorizontalDivider` containing `CreationMenu` on the left and `ToolMenu` on the right. The divider width is 6, its cookie is `SpawnMenuDiv`, right minimum width is 300 or 460 when screen width is at least 1024, and layout sets the left minimum to one third of the divider width. The border convar defaults to 0.1. Margins derive from `(screen size − 1024×768) × border`, clamp to 25–256, and become zero below either reference dimension. Resizing maintains the applicable left-width ratio.

The root also owns a 16×16 `DImageButton`. It uses `gui/spawnmenu_toggle` and `gui/spawnmenu_toggle_back`. Clicking hides/shows the tool pane and rearranges the same CreationMenu/divider objects rather than replacing the content browser. This native panel/layout/cookie contract is part of the original menu, not a fixed Fallout window size.

`cl_spawnmenu.lua` supplies original default tool tabs `Main` (localized tools tab, `icon16/wrench.png`) and `Utilities` (`icon16/page_white_wrench.png`). Main categories are Constraints, Construction, Poser, and Render, with original language keys. Custom tabs/categories are separately extensible hooks. `GM:PopulatePropMenu` calls `spawnmenu.PopulateFromEngineTextFiles`; original text-file parsing/population is an engine boundary, not an invented CSV browser.

`CreationMenu` derives from `DPropertySheet`, disables tab fade, reads `spawnmenu.GetCreationTabs`, and sorts by original `Order`. It creates sheet placeholders then uses a zero-delay timer to run each tab's factory, parent/dock its child and save its `ContentPanel`. Despite an older nearby comment mentioning first paint, the observed executable path uses the timer; preserve the code's timing rather than the comment.

Original creation tabs are Content (-10, application_view_tile), Weapons (10, gun), NPCs (20, monkey), Entities (20, bricks), Vehicles (50, car), Postprocess (100, picture), Dupes (200, control_repeat_blue), and Saves (200, disk_multiple). Equal-order tabs must retain registry/sorting behavior rather than an invented tie-break. NPCs include a `DDrawer` toolbox with convar-bound AI controls and the `gmod_npcweapon` chooser. Weapon registration autorefresh updates categories on the following frame. Entity/weapon/NPC/vehicle tabs build from original `list` registries and their language/category/icon metadata.

The Content factory creates `SpawnmenuContentPanel` (`DPanel`), its divider, `ContentSidebar` (`DPanel`) and `DTree`. It adds Browse, enables modification/search, calls `PopulatePropMenu` then `PopulateContent`, and moves/expands Browse. The right side switches between persistent `ContentContainer` panels, hiding the previous panel before assigning the next. The divider cookie is `SpawnMenuCreationMenuDiv`; left width is 192, and size-dependent minimums preserve the actual tree/browser layout. Tree drag-hover clicks are enabled; tree selection dispatches `ContentSidebarSelection`.

`ContentContainer` derives from `DScrollPanel` and owns a `DTileLayout` with 64 base units, a `SandboxContentPanel` drag/drop identity and selection canvas. Its read-only status is the inverse of whether changes trigger `SpawnlistContentChanged`. It provides original layout, clear/copy/serialization, rebuild-all, right-click label insertion, and multi-selection rerender/resize/delete behavior. This browser is not a fixed six-by-five grid.

## Prop browser, icons, model previews and spawn operation

The traced chain is original CreationMenu → SpawnmenuContentPanel → custom/game/addon ContentContainer → original `model` content callback registered by `lua/vgui/spawnicon.lua` → SpawnIcon with ModelImage child → click → `gm_spawn(model, skin, body)` → server `CCSpawn` → `Spawn_SandboxModel` → `GMODSpawnProp`/ragdoll/effect → `DoPlayerEntitySpawn` → permissions/counts/undo/cleanup. The 290-entry curated catalog can feed `spawnmenu.AddPropCategory` and content records with original model/skin/body metadata and a separate host-form identity mapping.

`lua/includes/modules/spawnmenu.lua` wraps the original native spawnmenu table before declaring its Lua module. `PopulateFromEngineTextFiles` clears `PropTable` before `spawnmenu_engine.PopulateFromTextFiles` supplies filename/name/contents/icon/id/parentid/needsapp records. Clearing prevents duplicate trees on reload after edits. `SaveToTextFiles` is likewise native. The native parser's precise disk paths and precedence remain unresolved, while the Lua record contract is established.

`contenttypes/custom.lua` recursively constructs editable spawnlist nodes from `id`/`parentid`, lazy-populates each container by `object.type`, and selects the first visible list. `needsapp` controls visibility through `IsMounted`; missing mounts have explanatory engine-game/localization tooltips. Addon lists are read-only. Save serializes nodes and content to version-3 KeyValues records; revert clears the tree, reloads native records and reselects on a zero-delay timer. Folder/node drag/drop and icon resizing mark changes, enabling the sidebar Save/Revert controls and protecting language refresh.

`contenttypes/gameprops.lua` builds the mounted-game tree from `engine.GetGames`, plus GAME/All and Garry's Mod, and enumerates `folder/*.mdl` through each node's path ID. It sorts filenames case-insensitively, dispatches the original model content callback and switches panels. A selected folder is retained so revisiting it need not rebuild icons. Game content remount clears/rebuilds relevant nodes. `addonprops.lua` enumerates downloaded/mounted addons with model counts, recursively finds their models through addon title path IDs, and provides original workshop/autospawnlist actions. FNV should supply a curated mounted-content facade rather than expose unrelated raw archives.

Search is explicit Enter or magnifier-click, rather than assumed live per-keystroke filtering. `contentsearch.lua` owns a `DTextEntry`, magnifier button and read-only result ContentContainer. F1/Escape dispatch menu close. `StartSearch` opens the menu, requests text focus, clears the entry, and clears `HangOpen` after 0.1 seconds; server `GM:ShowHelp` sends this hook to the client. Search obtains `search.GetResults` with the tab's provider type and `sbox_search_maxresults` (default/minimum 1024). Native/library aggregation/ranking still needs `lua/includes/modules/search.lua` evidence.

`cl_search_models.lua` lazily indexes models from `models/` in the GAME filesystem, incrementally recursing one queued directory per Think and reporting original notification progress under `SandboxSearchIndexing`. A one-second timer emits `SearchUpdate`; remount resets the index. All space-delimited terms must match each candidate's path; common `models/`/`.mdl` text is excluded unless a term requests a direct `.mdl` path, and useless models are skipped. Prop results cap at half the global result limit. Entity/NPC/vehicle/weapon providers match localized display names or class identifiers, suppress nonspawnable weapons, sort their results and cap each at a quarter of the limit.

SearchUpdate rebuilds only while the search result panel is selected. When closed, it records a rebuild flag and processes it on the next Paint; the original comment explicitly says Think caused a one-frame duplication. Equal result counts discard temporary newly created icons without rebuilding. This specific original guard informs regression tests; it does not prove the current HWND flicker has the same cause.

`SpawnIcon` derives from `DButton`, disables double clicking, creates a ModelImage child with input disabled, retains model/skin/nine-character bodygroup state and defaults to 64×64. Hover draws `gui/sm_hover.png` through GWEN texture borders with original real-frame-time fade; drag suppresses hover, depression insets the model image by 6, and PaintOver also draws selection marks. Ordinary hover does **not** spawn or select a tool.

The model content callback applies optional icon dimensions, model/skin/body, sets its tooltip, then on click plays `ui/buttonclickrelease.wav` and sends `gm_spawn` with all three identities. Right-click provides copy, creator Tool Gun, rerender-one/all, original IconEditor, resize and delete; read-only content suppresses edit/delete/resize. Creator selection sets `gmod_tool creator`, `creator_type 4`, model name and skin/body override. These exact callbacks are reusable behavior, not a Fallout prompt.

ModelImage receives `SetModel`, `SetSpawnIcon`, `RebuildSpawnIcon` and `RebuildSpawnIconEx` delegation. Its implementation/cache naming/render queue is **not present as a Lua file in the inspected cache** and remains a native/class-resolution boundary. Do not claim a hypothetical `lua/vgui/modelimage.lua` file was staged. `cl_init.lua:16` includes `gui/IconEditor.lua`; that editor's complete adjustable-model/camera/render-target dependencies still require its own direct read. `DModelPanel` is a separate real-time preview primitive, not the ModelImage implementation: it creates a no-draw ClientsideModel with IK disabled, chooses a walking sequence, starts a panel-bounded `cam.Start3D`, applies original lighting/color/blend/scissor state, draws the model, restores lighting/scissor and ends 3D. Its default layout rotates yaw with RealTime and advances animation only when enabled. Preserve the distinct icon cache versus interactive preview contracts.

`commands.lua:121` registers `gm_spawn` to `CCSpawn` (skin numeric or 0, body optional). `Spawn_SandboxModel` requires a valid player, rejects dead non-admin players, nil/path traversal and non-`models/*.mdl` paths, normalizes separators/case, calls native model validation, asks `PlayerSpawnObject`, then classifies valid physics prop/ragdoll/otherwise effect. Errors use an original error notice plus `buttons/button10.wav`; duplicate same-tick limit errors are suppressed.

`GMODSpawnProp` (`commands.lua:286`) asks `PlayerSpawnProp`, creates via `DoPlayerEntitySpawn`, dispatches `PlayerSpawnedProp`, repairs clearly invalid physics bounds when applicable, enables the source spawn effect, records undo with player/entity/model text, and adds props cleanup. `player.lua:48` defaults prop permission to `ply:CheckLimit("props")`, and `PlayerSpawnedProp` at 131 increments that count. These hooks remain extension/permission boundaries, not permission checks to omit in the host bridge.

`DoPlayerEntitySpawn` (`commands.lua:344`) traces 2048 Source units from player shoot position along eye angles, filtering player and vehicle, unless an explicit trace override exists. It creates the appropriate entity, applies model/skin/body, creator and yaw plus 180 (ragdoll pitch -90), spawns/activates, computes a model-nearest-point flush offset against the hit normal, adjusts each physics object for ragdolls, sends the corresponding original achievement event, and fixes partial wall penetration using OBB-axis traces. Host reference creation must preserve these intent/placement checks with translated host geometry, not arbitrary point placement. `prop_tools.lua:39` sets native spawn-effect state; visual implementation is another native/entity boundary.

The icon dependency is broader than PNG lookup: source model identity, selected skin/bodygroups, model materials/textures, mounted virtual paths, VGUI rendering and icon cache generation may participate. The current FNV lowercased-path/FNV1a32 PNG cache is an adapter-specific cache; it is not established as the original ModelImage cache. The exact mismatch, rather than a supposed missing substitute asset, must be tested when an icon fails.

## Tool selection and context-menu relationship

ToolMenu is a DPropertySheet containing ToolPanel per registered tab; ToolPanel divides the category list from active ControlPanel and includes a live text quick filter plus disabled-tools checkbox. Categories sort by localized tool names, use saved expansion cookies, and bind disabled status to `toolmode_allow_<name>` and original `CanTool` checks (including query button 4). Every 1.5 seconds tool tabs update permissions and the missing-toolgun/disabled-selected warning. Quick filter restores pre-search category expansion state when cleared. Controls derive from original DForm/ControlPanel and include original material/rope/prop selectors, convar-bound sliders/checks/colors, presets and numpad binders.

Category item `DoClick` invokes `spawnmenu.ActivateTool(button.Name)`. The module finds the registered item, runs its original Command unless `noCommand`, obtains `controlpanel.Get`, initializes it once through its original CPanelFunction, then activates its panel/tab and selection text. There is no hover-to-activate handler in the original ToolPanel. The Tool Gun report closes the resulting `gmod_tool <mode>` server/SWEP chain. The startup selection uses `gmod_toolmode` and calls activation with `noCommand=true` because it restores presentation for already selected state.

Spawn and context menus are mutually coordinated. ContextMenu derives from EditablePanel specifically so children can receive keyboard input. It enables world clicking, creates a DCategoryList canvas, and on open reparents the same active ControlPanel into its lower-right canvas when `ContextMenuShowTool` allows it. Close restores its original parent/position, remembers cursor, disables input, and follows HangOpen semantics. The control canvas is 320 wide, height capped at 80% of screen, inset 50 pixels from right/bottom. This is original shared control state, not a second independently built tool dialog.

ContextMenu forwards mouse press/release to original GUI hooks with `gui.ScreenToVector(input.GetCursorPos())`; therefore host cursor rays differ from normal eye-angle prop spawning. Desktop widgets come from `list.Get("DesktopWindows")`, a left DIconLayout of DButton/DImage/DLabel widgets, and per-widget original DFrame initialization. Its input toggle mirrors the 0.180-second source menu guard. Source `properties` entity actions and engine world-clicker dispatch remain separate dependencies requiring the original property modules/native boundaries. A single host input owner must translate these services without accidentally forwarding an Activate/use event to the opener.

Dupes and Saves creation tabs are original DHTML/JavaScript systems, not ordinary prop icons: they use JS_Language/JS_Workshop/WorkshopFileBase and original `asset://garrysmod/html/dupes.html` or save page. Dupes list `dupes/*.dupe`, use `.jpg` previews, arm via `dupe_arm`, check `CanArmDupe`, and optionally download/publish through steamworks. A local duplicator Tool Gun does not automatically require exposing workshop upload/download; preserve the original local UI dependency and classify network/workshop features separately. Their full HTML/CSS/JS closure is unresolved until staged/read, rather than replaced with a lookalike.

## Comparison with current FNV implementation

The independently audited current code preserves a persistent HWND; per-frame window recreation is therefore **not** a supported explanation for flicker. It currently uses a fixed 1140×720 GDI/Tahoma six-column/five-row browser and a lowercased SourcePath/FNV1a32 PNG cache, without the verified original panel lifecycle or established SpawnIcon/ModelImage renderer. It is a temporary implementation, despite a prior positive visual playtest.

Current hover handling arms custom Duplicator/Remover indices 7/29. This trigger is now demonstrably different from the directly read original ToolPanel: original activation happens on item DoClick, while hover belongs to visual feedback. Preserve the working curated catalog/form bindings, conversion provenance, native reference creation/collision adapters and tested inventory behavior while replacing only the evidence-backed menu boundary under the integration owner's control.

Likely causes to test, not confirmed faults: incomplete popup/focus ownership across Fallout and the overlay, repaint/invalidation artifacts within the persistent HWND, incorrect GUI/world mouse event routing, stale/null adapter icon-cache entries, package/material/model identity loss, and opener key dispatch competing with Fallout interaction/menus. A runtime trace must correlate visibility changes, actual input command edges, focus transitions, paint invalidation and failing source identities. The real original toggle/hang-open contract gives a concrete reference for that trace.
